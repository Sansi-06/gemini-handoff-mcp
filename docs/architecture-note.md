# 让免费本地智能体借用云端大脑

## 一、卡在免费额度上的真实麻烦

在本地用 Antigravity 这类编程智能体写项目，免费账号很快就会碰到一个很现实的坎。日常改几行代码、跑一下脚本、查个报错，本地轻量模型都能应付。一旦遇上跨十几个文件的架构调整，或者要啃完一整份几万字的接口文档再动手，轻量模型的推理深度和上下文长度立刻见底，额度也会在几轮长对话里烧空。

另一边，很多开发者手机和浏览器里都开着 Google Gemini APP。哪怕只用免费额度，网页端和客户端给出来的长上下文吞吐、深度搜索与高阶规划能力，都比本地免费档位宽裕得多。麻烦的地方在于，网页里的 Gemini 碰不到你硬盘上的代码，也敲不了终端命令。于是大家习惯了最笨的办法，把十几段源码一段一段复制到网页里问方案，等网页吐出几千字建议，再人肉贴回本地编辑器里逐行改。

我做 `gemini-bridge-mcp` 这件事，起初就是想把这段来回复制粘贴的活砍掉。思路很朴素，让云端 Gemini APP 专门负责想清楚怎么做，让本地的 Antigravity 专门负责读文件、改代码、跑测试。

## 二、为什么放弃浏览器模拟，改走官方连接器

GitHub 上其实早就有不少把本地编程工具连到 Gemini 网页版的项目，像 `BowTiedSwan/gemini-mcp` 或 `Walkoud/gemini-browser-mcp`。它们大多靠 Playwright、Chrome 调试协议或者浏览器插件，在后台打开一个网页窗口模拟人工点击输入。

我一开始也考虑过这条路，后来还是放弃了。原因很直接。网页前端经常改版，样式名一变脚本就断，维护起来没完没了。更麻烦的是风控问题，自动化脚本高频操作登录态页面，撞上验证码或者触发账号异常的代价太高。此外，这种方案只能绑死在开着浏览器的那台电脑上，手机端完全用不了。

后来我注意到 Gemini APP 的设置里开放了 Connected Apps 下的 Custom apps，支持直接接入符合 Streamable HTTP 规范的远程 MCP 服务。这条路把方向反过来了。本地不再去抓网页界面，而是自己起一个标准 MCP 服务，让 Gemini APP 按照官方协议主动过来领任务、读材料、交报告。

整个服务用 Node.js 22 原生模块写成，没有引入任何第三方 npm 依赖，跑起来常驻内存不到 30 MB。因为走的是标准 JSON-RPC 2.0 协议，只要 Google 继续维护这套官方连接器入口，网页界面怎么改版都不会影响工具运行，手机和网页端也都能直接唤起。

## 三、把大脑和手脚拆开的双向跑法

这套桥接工具在仓库里拆出了两条清晰的通路。

第一条是本地往云端派活。在 Antigravity 准备处理复杂调研或大范围重构之前，先通过命令行 `gemini-bridge push-repo` 把项目目录同步到中转沙箱。接着用 `gemini-bridge dispatch` 建一张任务单，写明目标、约束和希望拿到的文档结构。命令行会生成一段简短提示词，贴进 Gemini APP 以后，云端模型先调用 `get_task` 和 `claim_task` 把任务锁住，再按需调用 `list_repo_tree`、`search_repo_code` 和 `read_repo_file` 按行翻看源码。分析完成后，它调用 `submit_task_result` 交回一份精简摘要和一份完整报告。最后本地 Antigravity 跑一条 `gemini-bridge pull`，只花很少的本地上下文读完摘要，就能照着高阶方案动手改文件、跑测试。

第二条路是反过来走的，从手机往电脑派活。平时出门在外，在手机端 Gemini APP 里聊出一个新功能拆解，只要让它调用 `propose_task`，这份方案和建议步骤就会写进中转队列，标成待审核提案。等回到工位打开电脑，本地跑一句 `gemini-bridge proposals`，就能把路上聊出来的方案直接拉下来落地。

为了避开部分账号接入远程 MCP 时在动态 OAuth 注册环节容易卡住的问题，服务端除了完整实现 OAuth 2.1、PKCE 和 RFC 7591 动态注册之外，还留了一条多账号专属密钥通道 `/mcp/u/<key>`。在 Connected Apps 里填入对应路径并选无鉴权模式就能直连，服务端用恒定时间比对校验密钥，同时把不同账号的任务和审计日志隔离开。

## 四、给云端读本地代码划清安全红线

把本地项目送到云端让大模型看，最让人担心的就是密钥和隐私文件顺手漏出去。我们在客户端推送和服务端读取两头都加了硬限制。

在本地执行 `push-repo` 时，脚本默认跳过 `.git`、`node_modules`、`venv`、`dist` 这类目录，直接拦截 `.env`、各类 `.pem` 和 `.key` 私钥文件，以及路径里带 `credentials` 或 `secret` 字样的文件。单文件超过 512 KB 或者检测到二进制特征也会自动跳过，避免数据库文件和编译产物误传。

到了服务端，所有文件工具都被关在各自的根目录沙箱里，每次读写都会先走 `fs.realpath` 校验真实路径，拦住 `..` 路径穿越和符号链接逃逸。更重要的是权限切分。同步上去的代码目录和笔记目录对 Gemini APP 完全只读，云端模型只能往专门的交换目录写报告，而且每次增量改写都会自动留快照，方便随时回退。

## 五、绕不开的代价与当前边界

把这套工具真正用起来以后，有几个现实限制必须摆在明面上讲。

第一个门槛是运行环境。如果你想实现电脑关机以后手机还能随时往队列里发提案，确实需要一台 24 小时在线的机器，比如一台便宜的云主机，或者利用带免费额度的 Docker 容器托管平台来跑。如果平时只在工位电脑前配合使用，其实不用买服务器，直接在本地起服务再配一条免费的 `cloudflared` 临时隧道就能跑通，关机就停。

第二个限制来自平台侧。Gemini APP 的 Custom apps 入口目前对账号地区、英文界面和活动记录开关都有要求，并非每个账号打开就能立刻看见。碰到暂时没开放入口的账号，只能退回用 Google Docs 扩展做文件中转。

第三个待补齐的环节是半自动触发。现在从本地派完任务到云端接单，中间还隔着把一行提示词贴进 Gemini APP 的动作，结果交回来以后也要在本地敲一句拉取命令。后面可以考虑在本地加一个轻量守护进程监听完成事件，把人工搬运的最后两步也省掉。

## 六、这件小工具算不算有用

刚写完的时候我也算过一笔账。为了多用一点云端免费额度，还得操心隧道或者找地方挂 Docker，听上去挺折腾。后来在几个大项目上跑了几轮才看明白，它真正省下的并不仅是几块钱调用费，而是把“深度想清楚”和“动手改正确”拆给了最适合干这件事的两端。免费账号在本地本来够不着高阶规划模型，通过这条协议桥接，本地工具借到了云端的长脑子，云端对话也长出了能碰硬盘的手脚。工具本身只有几千行原生 Node 代码，没有黑魔法，但对被本地额度卡住的独立开发者来说，这条路跑得通，也值得开源出来一起继续改顺。
